# Governance

UML Studio is currently maintained by [PKDGOOD](https://github.com/PKDGOOD). It is a small, maintainer-led project; no foundation, commercial support contract, or service-level agreement is implied.

## Decisions and review

Routine fixes are reviewed in pull requests. Significant model, file-format, dependency, security, or roadmap changes should start with an issue describing the problem, alternatives, compatibility, and acceptance criteria. The maintainer makes the final merge/release decision and records material rationale in the issue or PR.

Contributions are evaluated for data preservation, correctness, accessibility, maintainability, scope, tests, and compatibility—not contributor identity. A second reviewer is preferred for security and schema changes when one is available. The project does not require two-person approval while it has only one maintainer.

## Releases

Use the [release checklist](docs/releases.md). Only the maintainer publishes releases. Alpha status and unresolved limitations must remain visible. Contributors should not infer support commitments from an unreleased version field.

## Becoming a maintainer

Consistent, reviewed contributions and demonstrated care for users can lead to a maintainer invitation. Access should be granted explicitly, with the minimum permissions required and two-factor authentication. Changes to maintainership should be documented here.

## Conduct and conflicts

Follow the [Code of Conduct](CODE_OF_CONDUCT.md). Disclose relevant conflicts of interest when proposing changes. If the maintainer cannot continue, they should announce maintenance status and either nominate a willing successor or clearly archive the project; there is no promised handover schedule.
