# 공개 알파 원자 단위 실행 계획

상태: **실행 시작 / 2026-09-27**. 총 **145개 작업**의 실제 상태와 증거는 [실행 현황](../execution-status.md)에서 관리합니다. 기록되지 않은 작업은 **Planned(계획됨)**입니다. 첫 배치에서 A01.01–A01.11 및 A07.03을 로컬 검증했으며, 커밋 검토·원격 CI·공개 판정은 남아 있습니다.

[영문 기준 문서](../atomic-execution-plan.md) · [제품 기획안](product-spec.md) · [단계별 실행 계획](../public-alpha-plan.md)

기존 A01–A14는 여러 결과물을 포함하는 **작업 묶음**으로 남기고, 실제 실행은 `A07.01` 같은 하위 작업 하나씩 진행합니다. 아래 모든 작업에 결과물, 직접 선행 작업, 기획/인수 ID, 규모, 완료 증거를 지정했습니다. 선행 관계·규모·기획 ID는 영문 기준 문서와 같습니다.

## 1. 원자 단위의 기준

한 작업은 **하나의 동작 계약 또는 하나의 검증 산출물**을 완성합니다. 파일 하나나 함수 하나를 뜻하지 않습니다. 같은 동작을 안전하게 바꾸기 위해 필요한 파서·엔진·UI·테스트는 함께 변경할 수 있습니다.

- 결과를 독립적으로 검토하고 의존성 역순으로 되돌릴 수 있어야 합니다.
- 구현과 그 동작의 정상/실패 검증은 같은 작업에 둡니다. 기본 브랜치를 깨뜨리는 테스트만 먼저 합치지 않습니다. 기존 결함 재현은 별도 재현 자료/명시적인 기대 실패로 기록하고, 수정 작업에서 일반 통과 회귀로 바꿉니다.
- **S 1–2시간 / M 2–4시간 / L 4–8시간**은 집중 작업과 해당 검증을 포함하는 초기 추정입니다. 사람의 엔지니어링 공수이며 자동 실행 시간 약속이 아닙니다. 하루를 넘기거나 결과가 둘 이상이면 착수 전에 `.a`/`.b`로 더 쪼개고 선행 참조를 갱신합니다.
- 기본은 한 번에 구현 작업 하나, 한 PR에 하위 작업 하나입니다. 서로 떼면 성립하지 않는 변경만 함께 묶습니다. 무관한 리팩터링·기능·의존성 계열은 별도 작업입니다.
- 이미 동작하는 기능은 재작성하지 않습니다. 현재 결과를 검증해 증거로 닫습니다. 현재 체크리스트의 체크 여부만으로 완료 처리하지 않습니다.
- 검증에서 새 결함을 찾으면 원인/동작 하나의 수정 작업을 추가합니다. 원래 인수 검증은 수정과 재실행까지 미완료입니다.

## 2. 실행·완료 규칙

`Planned → Ready → In progress → Review → Done`으로 관리합니다. 필요한 조건이 없으면 `Blocked`에 이유와 계속 가능한 독립 작업을 적습니다. **Ready는 직접/간접 선행 작업, 관련 결정·데이터, 필요한 실행 환경이 준비된 상태**입니다.

담당 기본값은 구현자, 검토는 메인테이너입니다. 표에 메인테이너로 표시한 항목은 계정·저장소 설정·사용자 관찰·공개 결정을 필요로 합니다. 다른 에이전트나 팀을 자동으로 배정한다는 뜻은 아닙니다.

각 이슈/PR에는 다음을 기록합니다.

```text
작업 ID / 상태 / 구현자 / 검토자:
기획 요구사항 ID / 인수 시나리오 ID:
이번 작업의 결과 하나 / 제외 범위:
선행 작업과 완료 증거:
변경 파일 (새 파일은 신규로 표시):
검증 명령 또는 수동 절차 / 실제 결과 / 커밋 / OS·빌드:
호환성과 복귀 방법 (해당 시):
남은 제한 또는 후속 작업 ID:
```

구현 PR은 저장소 필수 검사인 `npm run check`, `npm run build:app`과 해당 동작의 검증을 수행합니다. 파일/IPC 변경은 실제 패키지 경로를 추가로 확인합니다. 문서 작업은 `npm run repo:check`, `git diff --check`를 사용합니다. 테스트 개수만으로 저장·복구·사용성을 완료 처리하지 않습니다.

복구/히스토리를 포함해 새 권한 기능을 추가할 때도 A06.01의 호출자·요청·승인 ID 검증 정책을 적용합니다. 초기 IPC 작업 완료 이후 검증 없는 새 채널을 추가하지 않습니다.

현재 미커밋 작업을 먼저 목록화·보존합니다. 코드 복귀는 의존성 역순으로 하되 사용자 파일을 과거 형식으로 덮어써서 롤백하지 않습니다.

## 3. 단계별 통과 조건

`—`는 선행 작업 없음, `A05.*`는 해당 묶음의 **모든 하위 작업**을 뜻합니다. 별표는 통합 검증에 사용합니다. 숫자 순서가 전체 실행 순서는 아니며 실제 선행 관계를 따릅니다.

| 관문 | 통과 조건 | 다음 진행 |
| --- | --- | --- |
| G0 로컬 기준 | A01.01–A01.11 완료; 재현된 결함은 실패 사실을 기록 | 준비된 모델·저장·UI 작업 진행. 비공개 원격 CI는 별도 진행 가능 |
| G1 문서 무결성 | A02·A03·A04 전체 완료, F1–F4 수정 회귀 통과 | 지원 문서 변환의 보존성을 주장할 근거 확보 |
| G2 통합 후보 | A01–A12 전체 완료, 알려진 구현 공백 해소 | 최종 A13 인수 검증 |

재현 작업의 완료는 결함 해결을 의미하지 않습니다. G1/G2에서 해당 수정까지 통과해야 합니다. 후보의 코드·의존성·산출물이 바뀌면 영향받은 증거와 최종 연속 검증을 다시 확보합니다.

## 5. 실제 착수 순서

1. **A01.01 → A01.02 → A01.03:** 현재 작업 보존, 검증 기준 확보, 기획 대비 기능표 작성.
2. **A01.04–A01.11:** 데이터·F1–F5 재현·입력 한도·패키지 기본 흐름 확보. 각각 표의 선행 조건이 준비되면 진행합니다. A01.12/A01.13의 비공개 원격 CI 작업을 같은 순서로 억지로 묶지 않습니다.
3. **A02 → A03 → A04:** 데이터 유실 방지가 우선입니다. 직접 의존성이 준비된 A06.01, A09.01, A10.01은 독립적으로 진행할 수 있습니다.
4. **클래스 속성 수정 → DSL 보존 → 저장 → 재실행·열기**를 첫 기능 흐름으로 완성합니다. 선행 조건을 갖춘 A05.01/A05.03, A07.01을 연결한 뒤 시퀀스·포함 관계·나머지 유형을 완성합니다.
5. **A13 → A14:** 구현 자체의 검증은 각 작업에서 하고, 마지막에 패키지 통합·실측·독립 사용자 검증·공개 판정을 수행합니다.

저장/충돌의 실제 의존 경로는 **A02.08 → A06.02–A06.04 → A08.01 → A08.06 → A06.06 → A07.05**입니다. 충돌 화면 전에 보호용 스냅샷 작성기가 필요합니다. A07 묶음 전체가 끝나야 A08을 시작하는 방식으로 운영하면 안 됩니다.

같은 SyncEngine·문법·App.tsx·lockfile을 만지는 작업은 별도 통합 계획이 없으면 순차 처리합니다. 의존성이 독립적이라는 이유로 자동 병렬 에이전트 작업을 시작하지 않습니다.

## 6. 공수와 범위 관리

현재 분해는 S 22개, M 94개, L 29개입니다. **모든 작업을 수행한다고 가정해 규모 구간을 단순 합산하면 326–652시간**입니다. 이 수치는 이미 동작하는 기능의 검증 후 종결, 실제 난이도에 따라 크게 달라지는 초기 작업량 범위입니다. 리뷰·추가 수정 반복·파일럿 모집·계정/인증서 대기는 별도로 반영해야 합니다.

이전 25–38일 추정은 이번 상세 분해 이전의 추정이므로 확정 일정으로 사용하지 않습니다. A01.03/A01.10 이후 실제로 필요한 Ready 작업을 기준으로 다시 산정하고, 완료율보다 통과한 인수 조건과 남은 차단 항목을 보고합니다.

서명 자원이 없으면 로컬·소스 작업은 진행할 수 있지만 A14.04–A14.09를 완료 처리하거나 지원 바이너리를 광고하지 않습니다. 실험적 소스만 먼저 공개하려면 그 범위와 변경된 관문을 명시적으로 기록합니다.

스펙 주도 API/계약 테스트 제품 단계는 **이번 145개 알파 작업 밖**입니다. [제품 기획안](product-spec.md)의 별도 후속 기획으로 관리하며 알파 일정에 조용히 추가하지 않습니다. 기획 요구사항별 상세 작업 연결은 [영문 기준 문서의 Coverage](../atomic-execution-plan.md#coverage-and-exclusions)에 있습니다.
